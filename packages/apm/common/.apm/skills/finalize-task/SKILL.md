# Finalize Task

Use the existing task record and ordinary Git commands. No scripts, hooks, JSON schema, or fingerprint setup is required. This checklist guides behavior; it does not enforce compliance.

**Commit-message policy:** Do not add `Co-authored-by:` trailers to actual commits or copy-ready suggested commands. Pass this constraint to any delegated `git-commit` preparation and inspect the full proposed message, including body and trailers, before executing or emitting commands. Preserve legitimate other trailers, such as issue references and `BREAKING CHANGE:`. If conflicting guidance or external attribution cannot be resolved, report a blocker; do not assume this skill overrides host behavior, change configuration automatically, or bypass hooks.

## Follow-ups

Re-enter this skill at each final user-facing handoff for the same task, even without new edits while changes or publishing remain pending; a previous handoff does not discharge it. Skip interim progress updates and unrelated new questions.

- **Task notes:** keep in the existing task notes the cumulative owned paths/hunks, scope and acceptance, checks and review validity, learning disposition, and separate commit/push state across turns, resume, and compaction. Reconcile them with current Git before acting; do not rely on memory or the previous response, and do not infer ownership of all dirty work. If ownership or context is missing, report the blocker or ask; do not guess.
- **After refinement edits:** rerun affected checks and renew applicable independent review; reuse earlier evidence only while still valid. A same-task explanation without edits needs no new full suite or re-review.
- **Refresh Git first:** user commits, pushes, branch changes, and staging may have changed since the last turn. Re-verify destination and outgoing history; earlier suggested commands are never authorization.

## Procedure

1. **Confirm completion.** Check acceptance criteria, required guidance read, validation results, and self-learning disposition. Standard tasks require independent review of the final changes; Tiny tasks may omit review with a reason. After any edit, rerun affected checks and renew applicable review. Report missing evidence, failed checks, and unresolved findings as blockers.
2. **Inspect the worktree.** Run `git status --short`, `git diff`, `git diff --cached`, and `git diff --check`; disable Git pagers. Inspect task-owned untracked files separately. Account for accumulated task changes across turns and exclude unrelated or already committed work.
3. **Check authorization.** Commit and push each require separate explicit user permission. Without it, do not execute that action; prepare the remaining Git commands for the user's review and execution.
4. **Commit when authorized.** Use the available `git-commit` skill for preparation, subject to the commit-message policy above. Stage only reviewed task paths or hunks; preserve unrelated staging and stop if ownership cannot be separated safely. Inspect the complete staged diff and run `git diff --cached --check` before committing. Use `<type>(<optional-scope>): <concise imperative summary>` and a useful body when needed; `-m` is valid Git syntax, not a trailer.
5. **Verify the actual commit.** Inspect `git log -1 --format=fuller` and `git show --stat --oneline HEAD`, plus the committed diff. Confirm the intended changes and full message, including any hook-added content. If unexpected content or a prohibited trailer appears, stop and report it before push; do not amend, reset, or bypass hooks without authorization.
6. **Push when separately authorized.** Confirm the branch, intended remote, and outgoing commits; do not push unrelated history or guess a missing destination. Push explicitly without force, then compare `git rev-parse HEAD` with `git ls-remote <remote> refs/heads/<branch>`. Report push failures or mismatches, never success by assumption.

## Output

Give a proportional handoff at every same-task follow-up: concise cumulative outcome, exact checks and review results with their current validity, learning disposition and reason, blockers, and actual commit/push state. Report a commit identifier or verified remote state only after execution.

- **Self-learning:** always include the assessment's disposition and evidence-based reason in the final response, not just internal notes. For `updated`, link the owning edits and summarize the lesson and validation; for `proposed`, describe the proposal and why it was not applied; for `already-covered`, link the existing guidance and explain its coverage; for `none`, explain why the task yielded no reusable lesson. Missing assessment evidence is a blocker.
- **Git commands:** whenever task changes remain uncommitted or unpushed, always include one copy-ready shell block for the remaining actions, explicitly labeled as not executed and for the user to review before running. Regenerate the commands each time from current Git: cover all still-uncommitted task edits (including earlier ones) with explicit paths and an updated concrete message, and omit work already committed. If only push remains, give a push-only command when safe. For an uncommitted task, chain explicit task-path `git add`, `git commit` with a concrete Conventional Commits message, and `git push` with `&&` so the user can execute the reviewed sequence immediately. Do not split push into a separate block or insert an interactive confirmation. After an authorized and verified commit, include only the remaining push. This user-executed sequence is distinct from agent-executed publishing, which still requires the separate authorization and post-commit verification above. If all publishing is verified complete or there are no task changes, state that instead.
- Before emitting suggested commands, check their full commit message against the commit-message policy above, even without commit authorization. Resolve the repository path, task-owned paths, branch, remote, destination branch, and outgoing history from Git evidence. Use `git -C` (or an explicit `cd`), quote paths and message arguments safely, and stage explicit paths rather than `git add .`/`-A`. Preserve unrelated staging and mixed file changes; do not suggest a whole-index commit that includes unrelated work. If ownership, failed checks/review, detached HEAD, unknown destination, or unrelated outgoing commits prevent a safe sequence, state the specific blocker and provide only safe commands rather than inventing values or offering an unsafe publish sequence. Never force-push or bypass hooks. Suggested commands do not grant the agent authorization or count as executed actions.
