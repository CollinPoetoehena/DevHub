# Implementation Orchestration

The orchestrator remains the host's built-in active agent, such as GitHub Copilot Agent mode; it invokes this skill and carries out its procedure. Both this skill and the [planning skill](../planning/SKILL.md) retain the user's selected model/router and permission mode, for example Autopilot where supported. They do not create a new main agent or change those settings.

A clear, small task may take the direct path without a full plan. A larger unplanned request must return to Planning and wait for explicit approval of the saved contract; Autopilot and a request to "implement" do not approve a plan.

## Workflow

1. **Confirm the contract.** For planned work, begin in a fresh native session. Read the exact plan artifact, its current contents, applicable guidance, and supplied task status before edits. Require explicit human approval of that exact current version. Stop if the artifact or approval is missing, ambiguous, stale, changed, or unconfirmed; file presence is not proof of approval or unchanged contents. For a clear small task, confirm the user-authorized scope, constraints, and acceptance checks without inventing a plan path.
2. **Prepare the work.** For planned work, derive dependencies from approved work packages and verify acceptance criteria and write boundaries. For the direct path, use the bounded task and its checks without artificial decomposition. Use native research or exploration for substantial, bounded investigation when it materially reduces uncertainty; return concise evidence. Read-only explorers cannot save notes. If persistence is needed, use a writable helper and a unique authorized task/session location accessible to future workers, not a shared global temporary path.
3. **Assign bounded work.** Use fresh custom [Implementer](../../agents/implementer.agent.md) workers. Supply the approved plan path for planned work, or the explicit bounded scope and checks for a plan-free small task. Include applicable guidance, task ID, owned files, constraints, dependencies, relevant evidence, acceptance and test checks, and best-effort size/risk/cost intent (low for simple work, medium for complex work or review). These estimates are advisory, not model overrides. Use one worker for sequential work; parallel subagents or fleet are optional only when supported and tasks have independent, isolated write ownership. Wait for prerequisites and serialize competing writes. If required Implementer delegation is unavailable, report a blocker rather than silently substitute another role.
4. **Integrate and review.** Integrate completed packages against acceptance checks and run the applicable existing build, test, lint, type, and security checks on the combined result. Failed or partial work blocks its dependents; report the changes and failure. Obtain both independent native code and security reviews of the integrated change, in fresh assessment contexts and in parallel when the host supports it. Use actually available host review agents, skills, or tools; do not pretend user slash commands are agent-callable. A user-supplied independent native review result must cover the current integrated change. Return correctable implementation failures and blocking review findings to one fresh Implementer, then rerun affected checks and reviews of the corrected result. If a required check or review cannot run, or a blocker cannot be corrected within the approved scope and permissions, stop and report it. Unresolved failures or findings prevent a completion claim, not authorized remediation. Scheduling changes do not authorize contract changes.
5. **Report evidence.** Summarize actual changes, exact commands and outcomes, acceptance coverage, both reviews and their findings, unresolved issues, and limitations. Do not claim completion without the required validation and review evidence. Keep human **Verify** and **Observe** separate; do not publish or deploy automatically.

## Boundaries

This is a reusable procedure invoked by the existing native agent, not a custom orchestrator agent. It does not switch mode, select a model, alter permissions, or enforce controls; the host controls its tools, model/router, and approvals. Preserve existing user changes. Stop for missing approval, unclear requirements, failed prerequisites, or a material requirement, architecture, dependency, security assumption, or other scope change. Return such changes to interactive planning and renewed approval; do not silently amend the contract. Do not commit, push, deploy, or perform destructive actions without authorization. Respect denied effects rather than switching tools or rewriting commands to bypass them.
