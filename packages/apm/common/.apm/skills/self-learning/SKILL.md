# Self-Learning Assessment

Assess every implementation task, including Tiny tasks. This is controlled maintenance, not model training or permission to change policy.

## Procedure

1. Read the task evidence: corrections, failures, review findings, checks, and recurring friction. Inspect existing guidance before proposing a rule. If required evidence or guidance is missing, report the gap instead of inventing a lesson.
2. Retain only lessons that materially improve future work beyond this one task. Prefer correcting an existing rule to adding another. Reject redundant, speculative, cosmetic, or one-off details. Existing coverage and no durable lesson are valid outcomes.
3. Select the owner: project-specific knowledge stays in the project; shared role boundaries in an agent; stable constraints in instructions; repeatable procedures in a skill; human-facing context in the owning documentation.
4. In the owning repository, make authorized focused updates and update its changelog where maintained. Do not edit installed package copies or sibling/global files. When the owner is unavailable or outside scope, record a proposal and its reason instead.
5. Obtain explicit approval before changing enforcement, tool permissions, or publishing policy. Do not weaken checks to resolve a failure. Use available `manage-skills` or `agent-customization` procedures when relevant.
6. Validate retained edits with the owner's existing commands, metadata and links. Add them to the task's paths and evidence before final review; later edits require renewed applicable validation and review.

## Output

Record `updated`, `proposed`, `already-covered`, or `none` in persistent task evidence. For retained lessons include observation, reuse rationale, owner, action, and validation; for proposals include why they were not applied. For `none`, give a brief evidence-based reason. Missing evidence is a blocker, not `none`. Do not claim a proposal was saved or that the model learned persistently.
